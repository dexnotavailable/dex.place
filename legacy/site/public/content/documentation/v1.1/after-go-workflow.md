<a id="deliverable-and-scope"></a>
## Deliverable and scope

Deliver the whole first workable website described by this package. A successful room, attractive screenshot, generated asset, green unit test or running dev server is an internal milestone, not the final product.

The first version includes all four destinations, the connected platformer and katana, selected CC0 animation, terminal/boss/documentation-ZIP flow, physical document pages, nine illustrations and viewer, donation methods, audio behavior, responsive controls, and the documented failure/return paths. Original character animations and story captions remain later improvements. Use [16](copy-and-input-contract.md) for literal visitor copy and supplied inputs.

The build should be deliberate enough to judge atmosphere and responsive enough to improve through play. Workable does not mean perfect or award-winning. It also does not mean blank rooms, placeholder downloads, silent missing features, mismatched asset packs, dead buttons or a desktop-only page described as mobile-ready.

Dex's go sets a high taste bar: cinematic, somewhat emotional and surprising. Inspect actual composition, audio and transitions in addition to every button/dropdown/action state. Use18's action/state inventory, including the slash-open banner. Pivot on concrete poor outcomes; a mechanically working first version with weak atmosphere is unfinished.

<a id="stage-1-storage-only-when-the-forecast-requires-it"></a>
## Stage 1 — Storage only when the forecast requires it

<a id="establish-the-need"></a>
### Establish the need

Forecast additional physical storage for the isolated website checkout, missing dependencies, one selected model/runtime, temporary download/extraction duplication, build outputs, media exports and one rollback build. Count actual new physical bytes rather than path labels or already archived assets. Retain an 8 GiB working reserve beyond the forecast peak, revising it only from measured workload. Use the designated active-work volume and bulk archive; do not silently fill the system drive. Cleanup is conditional on this forecast. Private drive snapshots and candidate-file inventories are excluded.

<a id="rules-for-selecting-cold-files"></a>
### Rules for selecting cold files

- Use age as a lead, not authority. Last write/access timestamps alone cannot distinguish an unused file from an old file still referenced by a current app, model, project or proof.
- Resolve reparse points and physical volume before estimating reclaim. Do not recursively follow junctions during inventory or double-count the same bytes.
- Check ownership, active process/task/config references, repository state and actual archive/replacement coverage. Prefer completed disposable build caches or inactive installers whose role is known.
- Keep active source/worktrees, runtime/model dependencies, current gallery art, saved games/worlds, credentials, private ownership records documents, private user input files, accepted release bytes and live proof/session stores out of blanket cleanup.
- Preserve active session and evidence stores; they are not a cleanup shortcut.
- If use is uncertain, skip that candidate and continue. Do not turn uncertainty into a broad “delete old things” action or make Dex audit hundreds of unrelated files.

<a id="reversible-archival-after-go"></a>
### Reversible archival after go

Go authorizes the requested conditional storage preparation using these bounded reversible rules. It does not imply permission to permanently discard unique personal files. Ordinary safe archival of verified inactive candidates does not need another per-file taste/approval menu; genuinely destructive or ambiguous user-data actions remain separate.

1. Record exact source and planned archive destinations under `private verified archive`, ownership, physical volume, counts/bytes and the reason the material is inactive.
2. Validate resolved absolute source/destination paths against the specific candidate/archive roots. Never operate recursively on a drive root, wildcard-derived target or unresolved junction.
3. Copy to A using one native Windows file-operation route. Verify relative file inventory, sizes and content hashes; detect source changes during copying and abort source retirement if the snapshot is no longer stable.
4. Verify any required owner references, or preserve an explicitly needed old-path mapping through an owner-approved method. Never leave an app/config/proof pointing to a missing asset.
5. Retire the verified duplicate at the original location as part of the reversible move only after archive verification succeeds. Preserve the archive and rollback receipt. No permanent deletion of the sole surviving copy.
6. Measure actual free-space change afterward; logical bytes are not promised allocated-space savings. Record any failed/partial move and restore the old path if necessary.

Stop cleanup once the forecast fits. If the safe candidate yield is insufficient, stage one smaller/compatible model configuration or reuse verified existing assets, document that resource decision, and continue the light website work. Do not enlarge this task into general workstation reorganization or delete protected material to make a model fit. A 15-minute initial metadata pass should produce a forecast and concrete candidates; repeating an unproductive scan is not progress.

<a id="stage-2-reconcile-specification-and-assets"></a>
## Stage 2 — Reconcile specification and assets

1. Snapshot the reviewed starting spec revision and carry its uncommitted files into the implementation checkout using the exact manifest rule in [13](build-readiness-and-scope.md). A HEAD-only worktree is insufficient. The handoff snapshot prevents lost context; it does not freeze visual tuning.00 owns the firm contracts and scene-checkpoint update policy.
2. Build the minimum asset register for the first playable: chosen CC0 animation, base architecture tiles, terminal parts, lift/platform parts, cable/bridge, section anchors, Daniel logo, approved gallery display sources and the audio plan.
3. For each asset record its role, source/license, intended destination, pixel scale, palette/material treatment, animation/attachment/collider contract and acceptance evidence. Unassigned decorative assets do not enter the build merely because they look good alone.
4. Follow10's production order: CC0 traveler and rough playable layout, individually generated foreground pieces, immediate assembly, then separate background depth roles. Compare that first actual scene against01's three scale studies for depth, silhouette, quiet space, pixel cohesion and readability. Tune the working view freely within the existing contracts; numeric guides are diagnostic. Keep the donor as authored and evaluate the actual shell/touch controls. Do not pre-generate the entire world's asset library before this composition works.
5. Existing illustrations remain display-only in the exhibit section. They are never model references, environment textures, loading screens or character sources. Kaizen/Convergence story remains separate.
6. Apply the literal-copy contract before coding UI. Header is `dex` and navigation, not a role line or sales slogan. Internal scene/audio direction must not become promotional interface text.

This stage establishes enough coherent material to build and a repeatable acceptance rule. It does not require finishing every future asset, every model or every musical cue before implementation starts. Repeat the asset check whenever a new batch is introduced during stage 3.

<a id="stage-3-complete-implementation-with-bounded-parallel-lanes"></a>
## Stage 3 — Complete implementation, with bounded parallel lanes

One integration owner keeps route state, download intent, content/asset manifests and final integration consistent. Bounded parallel lanes can own world/physics/map, DOM/content/export, audio/media, and independent verification. They agree interfaces first and do not independently rewrite shared state. Avoid running several GPU production jobs at once or evicting another active owner without authorization.

<a id="3a-isolated-build-and-usable-shell"></a>
### 3A. Isolated build and usable shell

- Recheck the real source/branch state. Create an appropriate active-work implementation branch/worktree after go; copy the exact reviewed docs and entry-point rules by manifest. Preserve unrelated dirty client/catalog work and the old public runtime. No commit or push unless Dex asks.
- Install only the selected necessary dependencies into the controlled environment. Record versions and disk footprint; do not install every available plugin or generator.
- Build the four real routes, layout, focus/pause rules, errors and persistent controls first. Readable content must remain usable when game assets fail.
- Use the actual reviewed public documentation export, selected local gallery inputs and donation facts as soon as their adapters exist. Fixtures stay in isolated tests and do not become final public content.

<a id="3b-prove-the-one-room-foundation"></a>
### 3B. Prove the one-room foundation

- Import the selected CC0 donor at its native dimensions, apply the documented clip/event mapping, and prove run/jump/dash/slash/landing/hurt/defeat without a cosmetic redesign.
- Author the room through Tiled and its normalized export; use independent terminal, lift, cable and bridge assemblies. Their visuals, collisions, interaction zones and sounds follow their owner transforms.
- Assemble the separate foreground and background sources in this real room early. Evaluate the overall image while walking/jumping and opening a panel; adjust the relevant asset, camera, light or spacing instead of fitting every object into a frozen diagram. At the accepted checkpoint, capture the scene and synchronize chosen presentation values to the owner docs/config.
- Prove movement/collision, platform carrying, slash timing, E/panel focus, reset and once-only download intent using the actual documentation ZIP once packaged.
- Move/duplicate objects and repeat an asset/map export. Fix source/export ownership rather than hand-patching runtime offsets.
- These foundational failures block multiplying the same broken system into four regions. Missing access to a physical phone does not block independent desktop/content work; keep its proof explicitly pending.

<a id="3c-expand-into-the-whole-place"></a>
### 3C. Expand into the whole place

- Complete arrival, Dispatch/arena, Archive, Exhibition Hall, Support Alcove and all documented connecting routes. A completed first room is not the final handoff.
- Add the existing sliceable targets, elevator states, safe anchors, camera boundaries and restrained atmospheric motion. Add no unregistered combat mechanics, inventory, narration or new destination.
- Integrate the complete documentation index and six physical-file targets, nine-image gallery/viewer, exact Ko-fi link and MB amount/QR flow.
- Verify desktop and mobile layouts as each section joins the integrated build. Keep controls readable while world framing stays wide; do not shrink touch targets to preserve a screenshot.
- Review the actual served-file tree as well as imports. Do not accidentally ship private authoring files, test sheets or unused legacy material because a public directory is copied wholesale. Preserve existing accepted download routes through their owner rather than deleting unrelated releases.

<a id="3d-produce-and-integrate-cohesive-media"></a>
### 3D. Produce and integrate cohesive media

- Use the local-first audio direction in14 and the compositions/loops in12. ElevenLabs remains reserved. A chosen local runtime is a production tool, not a new user-facing product or a reason to postpone the entire website.
- Start with the bounded audition and retain usable takes. Edit accepted cues and short effects into the specified exports; do not rerun broad model competitions or train a LoRA as an unrequested prerequisite.
- If a media route repeatedly fails without new evidence, change the relevant production method using documented proof and the authorized fallback budget. Continue independent implementation while the media problem is resolved. Do not pretend missing audio is complete.
- Check every world asset in composition, and every sound in context. A technically valid file with mismatched perspective, pixel density, light or tone is not automatically accepted.
- Keep the look cinematic and emotionally suggestive through scale, framing, light, silence and movement. Fun comes from responsive traversal, readable sword feedback and small spatial discoveries; no promotional copy is needed to explain it.

<a id="3e-harden-the-integrated-first-version"></a>
### 3E. Harden the integrated first version

- Remove fixtures, temporary broken controls, loading dead ends, debug overlays and unapproved copy from the reviewable build.
- Exercise stale/duplicate callbacks, failed loads, canceled encounters, history, returning focus, mute, orientation changes and unavailable clipboard/fullscreen/download behavior.
- Keep the docs synchronized with actual chosen parameters and source locations. New scope or a contradiction of a confirmed rule goes back to the owner process; routine tuning inside the existing contract is documented and verified without another taste menu.
- Provide the actual run/build instructions and a repeatable current build. Preserve sources, provenance and a rollback path for later improvements.

<a id="mobile-coverage-on-every-build-revision"></a>
### Mobile coverage on every build revision

- Primary real-device targets confirmed by Dex: **Samsung Internet on Android** and **iPad Safari**. Safari on the iPad is the stated default assumption; record the actual installed versions/device details when testing.
- Also exercise the supported phone/tablet layouts and current Chromium, WebKit and Gecko browser-engine paths where the available test tools support them. Android Chrome and iPhone-sized Safari layouts are additional coverage, not substitutes for the primary physical devices.
- Every runnable integrated build revision gets a mobile regression pass: navigation, one E/touch panel, movement plus action, orientation, safe areas, input fields and content reflow. Run the complete relevant matrix at milestones and final handoff; this does not mean rerunning every test after each keystroke.
- Baseline content widths:320, 360, 390, 430, 768, 820 and 1024 CSS px, plus actual device dimensions; portrait and landscape; normal/large text; touch and keyboard where applicable. Record tested browser/version, width, orientation and device versus emulation.
- On Samsung Internet and iPad Safari inspect real address-bar/viewport changes, multi-touch, audio activation/resume, ZIP behavior, gallery gestures and QR image saving. Bank-app QR import/recipient inspection needs the actual supported device/app path.
- “Every version” means every implementation revision and every variant in the declared support matrix. It is not a claim about all historic browser/OS releases. Expand the matrix when an actual required variant is identified.
- If real devices are not tool-accessible, prepare the complete reviewable build and give Dex one short concrete test URL/checklist at that point. Mark those rows pending until actual evidence arrives; never relabel desktop resizing as Samsung/iPad proof, and never stop unrelated work while waiting.

<a id="handoff-and-publication"></a>
### Handoff and publication

The handoff includes the exact runnable build/location, commands, sources and reviewed assets, spec revision, proof for the above journeys, measured limitations and a short prioritized improvement list. State locally verified and publicly verified separately. Do not claim a complete mobile/public result when required proof is missing.

Public promotion follows the scope of Dex's actual later go-ahead and the existing hosting owner. Preserve the old public site until the replacement passes the relevant gates and promotion is authorized. If a public-only gate needs input, first finish everything independently authorized and make the result concrete; ask only for that exact remaining action, with its reason.

No additional creative brief is required before starting after go. Optional art-story captions remain later. Actual device access, bank-app inspection or an external security/login prompt may need Dex at the corresponding concrete step; these are not reasons to ask for more slogans, colors, tool preferences or a new architecture menu now.
