<a id="control-coverage-rule"></a>
## Control coverage rule

For each SYS, DL, DOC, ART and DON row, and every movement/world-prop action in [02](world-and-gameplay.md) and [06](mobile-accessibility.md), record:

1. Where it renders, label/accessibility name, and bound content ID if repeated.
2. Pointer and keyboard behavior; touch behavior for relevant devices.
3. State before and after; route, focus and history effects.
4. Loading, empty, disabled, denial, error, cancellation, and repeated-activation outcomes where applicable.
5. Whether game input, audio or an external effect occurs.
6. Actual evidence reference and result: `pass`, `partial`, `fail`, or `not tested`.

Not applicable states need a reason. Do not create fake errors for an ordinary local button; do not skip real errors because the happy path looked correct. A repeated tile uses one control contract with content-specific binding checks.

<a id="required-visual-and-feel-proof"></a>
## Required visual and feel proof

Specification compliance and whole-result quality are both required. Preserve every documented requirement and its classification; if a proposed visual value needs refinement, record that change rather than silently removing it. Technical success, valid asset dimensions, matching ratios or passing controls cannot by themselves approve a scene that looks bad or plays poorly. Review the integrated experience as well as individual parts.

Capture arrival, Dispatch, active boss attack, victory result, a document pickup, readable article, gallery index/viewer, Donate method choice, minimum/maximum MB amount, ready/error QR, menu and mobile touch view. Include brightest and darkest scene backgrounds. Screenshots are artifacts of the real runtime, not ImageGen targets.

Keep plain runtime captures for all destinations and review the overall composition with actual controls visible. Annotate the initial representative scene, or a crowded/unreadable scene being repaired, when measurements clarify the problem; do not require the same measurement overlay on every room. Compare supported desktop/ultrawide/tablet/phone layouts and include Low/reduced motion so scale does not depend on expensive effects. Retain the existing mobile regression matrix. Also review normal panels with long titles/filenames, all four navigation labels, readable bank facts and large text. Accept a visually successful composition outside a starting numeric range when interaction/accessibility remain correct; record the chosen tuning in its owner doc at the checkpoint.

Capture short recordings showing movement/landing, one cable cut, each boss attack and safe response, pause/resume, touch multi-input and rapid navigation. Evaluate anticipation, contact timing, player silhouette, foreground occlusion, camera look-ahead and response latency. A build pass is not proof of feel.

Listen to complete music loops, their joins, each region transition and muted/hidden behavior. Log actual observations, not “sounds cinematic” without playback. No generation is approved merely because an API completed.

<a id="proof-format-and-stop-boundaries"></a>
## Proof format and stop boundaries

Store future proof under `private production review records` or a similarly named approved active-work project output. Each receipt records spec version, source revision, environment/device/browser, tested control/scenario IDs, actual result, evidence paths and limitations. Keep raw secrets and bank transaction data out of receipts.

Docs status and runtime status remain separate. Use “authored,” “reviewed,” “implemented,” “locally verified,” and “publicly verified” only for their actual scopes. Tests that manipulate an isolated fixture file are not real release-delivery proof. Opening a QR is not bank verification; bank-app inspection is not a donation.

Stop publication of the affected feature when recipient/QR fields disagree, exact artifact identity is uncertain, art appears outside its allowed section, browser flow requests unintended files, or critical mobile/content access fails. Continue independent repair work under the active implementation go; unresolved evidence does not erase authorization or establish success.
